# Marquee Events

Event management app. Monorepo: FastAPI backend + React/TypeScript frontend.

```
backend/    Event Management API (uv, ruff, mypy --strict, pytest)
frontend/   Marquee Events UI (Vite, React 19, oxlint, Prettier, Vitest,
            TanStack Query, Tailwind v4, shadcn/ui)
```

## Commands

Always run these from the repo root via `make` — never invoke `pytest`/`vitest` directly,
because the Makefile sets the correct working directory and environment.

| Task | Command |
| --- | --- |
| Install everything | `make install` |
| Run both dev servers | `make dev` |
| Backend tests (watch a single file: `make test-backend ARGS="-k name"`) | `make test-backend` |
| Frontend tests | `make test-frontend` |
| All tests | `make test` |
| Format + autofix | `make fmt` |
| Lint + typecheck | `make lint` |
| Everything CI runs | `make ci` |

`make lint` must pass before any commit. `make ci` adds both test suites and the
production build — it is the full pipeline equivalent, so run it before pushing.

## Planning — small discrete steps

Before implementing anything non-trivial, break it into the smallest steps that each
have their own failing test. A step is one behavior, not one feature. State the list
first, then work it one item at a time — test, implement, green, next.

- Do not build the whole structure up front. Create files when a step needs them, not
  because a plan predicted them.
- Each step should be independently reviewable and leave the suite green.
- If a step turns out to need two tests, it was two steps — split it.
- Do not implement ahead of the current step, even when the next one is obvious.

## Test-driven development — non-negotiable

This project is built test-first. When implementing any behavior change:

1. **Write the failing test first.** One test that captures the specific behavior being
   added. Put it in `backend/tests/` or beside the component in `frontend/src/`.
2. **Run it and confirm it fails** — and fails for the *right reason* (assertion failure,
   not an import error or typo). A test that has never been observed failing proves nothing.
3. **Write the minimum implementation** to make it pass. Do not add unrequested
   generality, config knobs, or abstraction layers "for later."
4. **Run the full suite** to confirm nothing else broke.
5. **Refactor** with the tests green, re-running after each step.

Rules that follow from this:

- Never write implementation code before there is a failing test covering it.
- Never modify a test to make failing implementation code pass. If a test is genuinely
  wrong, say so explicitly and explain why before changing it.
- Never delete, skip, `xfail`, or comment out a failing test to get a green run. A failing
  test is information; report it.
- Bug fixes start with a regression test that reproduces the bug.
- If asked to add behavior with no clear way to test it, raise that as a design problem
  rather than silently skipping the test.

## Conventions

**Backend**
- `mypy --strict` — every function annotated, including tests. No bare `Any`, no
  `# type: ignore` without a specific error code and a comment explaining it.
- Pydantic models are the contract. Validate at the API boundary; inside the app,
  trust the types.
- FastAPI dependencies via `Depends()` for anything needing test substitution — this is
  what makes handlers testable without mocking HTTP.
- No `print()` — ruff's `T20` rejects it. Use a module-level
  `logger = logging.getLogger(__name__)`.
- Business logic lives in modules that do not import FastAPI, so it is unit-testable
  without a client.

**Frontend**
- `strict: true` plus `noUncheckedIndexedAccess`. No `any`, no non-null `!` assertions
  to silence the checker — narrow the type properly.
- Prefer React Testing Library queries by accessible role/label over test IDs; tests
  should exercise what a user can perceive.
- All HTTP goes through `apiFetch` in `src/api/client.ts`. Calling `fetch` directly
  skips error handling and the `VITE_API_URL` base. One module per resource under
  `src/api/`, mapping the API's `snake_case` to `camelCase` at that boundary.
- `src/components/ui/**` is generated by shadcn — do not hand-edit it. Add components
  with `npx shadcn@latest add <name>`, and wrap rather than modify them.
- Import via the `@/` alias, not deep relative paths.
- Style with Tailwind utilities and the theme tokens in `src/index.css`. Do not add
  new CSS files or hardcode colors that bypass light/dark.

**Git**
- Never add a `Co-Authored-By` trailer or any other attribution footer to commit
  messages.
- Describe what changed and why. No emoji, no tool branding.

**Both**
- Prefer editing existing files over adding new ones.
- No comments that restate the code. Comment the *why* when a choice is
  genuinely non-obvious and someone would otherwise undo it.
- Don't annotate individual fixes. A comment explaining why a line changed
  belongs in the commit message, not the file — that includes config files.
